Which pages decline first? Ranking a content portfolio for refresh, honestly.

Ali Haider FlyRank ML Internship, Capstone September 2026

## abstract

How do you decide which of thousands of content pages to refresh first, without reviewing each one by hand? Working from a 30,000-page, 32-client anonymized export, a hand-written rule (stale content still getting search visibility) was compared against a Random Forest trained on 17 pre-decision page signals, validated by holding out 6 entire clients the model never trained on. On that honest split, the Random Forest measured a 0.749 ROC-AUC and a Precision@50 of 0.76, against a baseline that could not even be scored on the same slice because it only ever flags 17 of 30,000 pages portfolio-wide. Auditing a naive row-random split showed it would have overstated average precision by 0.147 for the same model, confirming client-grouped validation as the correct design rather than an optional extra. The result is packaged as a ranked, reason-coded action queue with a mandatory human-review gate — decision support for a content team's weekly triage, not a verdict on any single page.

01 Introduction

A content team can't manually review every page in a large portfolio to decide what to refresh next. Search performance data is available for every page — but knowing which handful to act on first, out of thousands, is a triage problem.

The starting point for this work is a simple hand-written rule: flag a page if it hasn't been updated in 180+ days and is still pulling meaningful search impressions. That rule is transparent and defensible, but it is narrow — across the whole portfolio it fires for only 17 of 30,000 pages. Most of the portfolio gets no answer at all.

This paper asks a narrower, answerable question: can a model trained on pre-decision, observable page signals rank a content portfolio for refresh review better than that hand-written rule — measured honestly, on clients the model has never seen? It is not a claim about how search engines rank pages, and it is not a causal claim that refreshing a page will recover its traffic. It is a claim about whether a specific, disclosed feature set and model can usefully order a queue of candidate pages for a human to review.

02 Data

All analysis in this paper runs on a single anonymized export shipped with the FlyRank ML Internship starter repository: data/raw/content_refresh_anonymized.csv.

Every field is a trailing, pre-decision signal about a page — search volume, competition, click-through rate, position tier, word count, content age, days since last update, engagement and scroll metrics — plus an anonymized client_id and content_id. No client names, URLs, or query strings are present in the export or reproduced anywhere in this paper.

Label definition

The target is is_declining_label: 1 when a page's trend_direction field equals down (a 30-day-vs-prior-30-day impression trend, bucketed by the data provider at roughly ±20%), 0 otherwise. This is an observed outcome label, not a synthetic one — but it means the label is a coarse, single-snapshot summary of a noisy trend, discussed further under Limitations.

Exclusions and why

  • Product decision flags excluded by the data provider. The export deliberately ships only observable, pre-decision signals — no internal health scores or "needs fix" flags — so a model trained on it cannot accidentally learn from a decision that already happened.
  • Label-source columns excluded from the feature matrix. trend_direction and trend_pct (the exact percentage the label is thresholded from) are never used as model inputs. Injecting trend_pct as a confession test collapses the problem to ROC-AUC = 1.000 (Methodology, leakage checks) — direct proof the label-source column carries the answer, and confirmation the harness would catch it if it slipped in.
  • 90-day rolling totals dropped from the final feature set. impressions_90d correlates at 0.918 with impressions_last_30d — one of the two windows the label is built from. Dropping the four 90-day-total columns cost only ≈0.006 ROC-AUC and ≈0.016 average precision, so the more conservative, fully-disclosed feature set was adopted rather than relying on "it probably isn't leaking much."
  • No client names, raw URLs, or query text appear anywhere in this paper — a public-safety pass was run on every section before deployment.

Two SEO beliefs worth stating up front, because they shaped which features were trusted:

  • Keyword search volume barely predicts the traffic a page actually gets — the correlation between search_volume and impressions_90d is 0.001 across the whole portfolio, and stays at 0.001 restricted to pages that already have impressions.
  • Click-through rate collapses hard with position, not gradually — mean CTR falls from 0.355 on page 1 to 0.055 in "deep" results.

03 Methodology

Assumptions

The problem is framed as binary classification with an observed label, not a synthetic one, which points toward interpretable baselines first: logistic regression for a coefficient story, then a tree ensemble if the comparison earns the added complexity. Gradient boosting was deliberately skipped this round — with a client-holdout test set of 2,325 rows and a hand rule that only ever flags 17 pages, a heavier ensemble was complexity the data didn't yet justify against a conservatively-tuned random forest.

Feature set

17 numeric features (search volume, competition, CPC, word/character counts, log-scaled 30-day-window session and click signals, days with impressions, content age, days since last update, CTR, average position, engagement rate, scroll rate, AI-traffic share) and 8 categorical features (competition level, content type, main intent, age tier, freshness tier, word-count tier, impression tier, position tier), one-hot encoded to a 60-column matrix. Missingness is flagged with explicit indicator columns rather than silently zero-filled, since missingness itself follows content_type in this export.

Baseline

The Week-4 hand rule: flag a page if days_since_last_update ≥ 180 and impressions_90d ≥ 500, scored by impression volume. It fires for 17 of 30,000 pages across the full portfolio — and, by chance, for zero of the 2,325 rows in the client-holdout test split, which is itself a finding about how narrow a single hand-written condition can be.

Validation design

Splits are client-grouped, not row-random: the 32 client IDs are shuffled with a fixed seed and 20% of clients (6 of 32) are held out entirely for testing, so no page from a test client is ever seen in training. This matters because rows from the same client share a site, a content strategy, and a baseline traffic level — a row-random split would let a model partly memorize a client rather than learn to generalize to one it has never seen.

This design choice was audited, not assumed. Re-running the identical model under a naive row-random split let 31 of the 32 clients appear in both train and test — and inflated every metric:

The gap is not attributed entirely to memorization — the two test sets also carry different base rates (0.542 naive vs. 0.391 grouped) because the 6 held-out clients happen to decline less often than the portfolio average, which is itself a real fact about deploying to an unfamiliar client. But the direction and size of the gap is exactly why every result reported below uses the client-grouped split.

Leakage checks

  • Confession test: injecting the literal label-source column (trend_pct) into the feature matrix drives ROC-AUC to 1.000 — confirming both that the label is fully determined by that column, and that the test harness would catch it if it were left in.
  • Overlap-window check: impressions_90d correlates at 0.918 with impressions_last_30d, part of the label's own construction window — a disclosed structural overlap. Dropping the four 90-day-total columns cost ≈0.006 ROC-AUC, so they were removed from the final model rather than kept on a "probably fine" basis.
  • Timeline check: every retained feature is a trailing, pre-decision fact about the page, not a downstream consequence of the labeling event.

The baseline can't be scored at Precision@K here at all: it only ever fires for 17 of 30,000 pages portfolio-wide, and this particular client split happened to hold out none of them. Its ROC-AUC of exactly 0.500 and average precision equal to the base rate are the honest "no information" values for a rule that never activates on this slice — the real cost of an extremely narrow hand-written condition, not a scoring bug.

On this client-grouped holdout, Random Forest measured higher precision at every K, a higher ROC-AUC (0.749 vs. 0.702), and higher average precision (0.618 vs. 0.524) than Logistic Regression — a directional result on one split, not a settled general verdict. Gradient boosting was not needed to clear the baseline by a wide margin on this data.

What the model leans on

Impurity-based and permutation importance agree on the same top signals: how consistently and how well a page shows up in search — days_with_impressions, log_impressions_90d, avg_position, and ctr — dominate. content_age_days, word_count, and char_count sit further down. None of these are the label in disguise, and none sit at the 0.9+ importance a leaked column would show. This lines up with the Week-1 discovery that word count barely separates declining from growing pages (2,909 vs. 2,848 median days) — length is not the lever; visibility is.

Where the model is wrong

Of 2,325 held-out rows, the model produced 555 false positives and 224 false negatives at a 0.5 probability threshold.

  • False positives cluster on pages with 0% CTR at a real position that are actually trending up or are brand new — the model reads "zero clicks at a real position" as decline, but a page that hasn't had time to accumulate clicks yet looks identical to one that's failing.
  • False negatives cluster on pages with avg_position = 0, the dataset's documented "no position data" code (not an actual top rank) — these pages are so close to invisible on every feature that the model has almost nothing to separate a dying page from one that never had traffic to lose.

05 Limitations & honest framing

  • Cross-sectional, not causal. This is one trailing 90-day snapshot. Nothing here shows that refreshing a page causes recovery — only that certain page profiles are associated with decline in this portfolio.
  • Validated on 6 clients out of 32. The 0.743 held-out ROC-AUC (final feature set, Section 4) is real but comes from one holdout of one size; a different random client split could move it, and no client from an industry vertical absent from this portfolio has been tested.
  • No visibility past the export date. A page ranked stale here may already have been refreshed since the data was pulled — the queue is only as current as the last export.
  • Thin at the extremes. The most-stale and 31–90-day freshness tiers together make up only 1.2% of rows (349 of 30,000) — confidence in that corner of the ranking is lower than the headline metrics suggest.
  • A documented "no data" code, not a real position. avg_position = 0 means no ranking data, not rank 1. Treating it as a real position is exactly the pattern behind the model's false negatives; the playbook (Section 6) routes these to mandatory manual review rather than an automated score.
  • Single-snapshot label thresholding. The declining label depends on a ±20%-style trend threshold set by the data export; a different export of the same underlying data used a >10%/-10% threshold in the same provider's own research, which shifts the balance of "declining" pages that definition produces. That's a real difference between two of the provider's own exports, not a rounding choice.

Claim, rewritten

Overclaimed version: "Random Forest is the clear winner: roughly double the precision, and I didn't need gradient boosting to beat the baseline."

Defensible version: On this client-grouped holdout, Random Forest measured higher precision@20/50/100, ROC-AUC, and average precision than Logistic Regression — a directional result on one split with one feature set, useful for decision support, not a guarantee that holds on every future client or export.

06 Ranked recommendations — the action playbook

The deployed model score is not handed to a content team as a raw probability. It's mapped to a small set of explainable archetypes first — patterns already understood and defended above — with the general model score as a fallback for real risk the named archetypes don't cover.

  1. 1

    Refresh review — stale & still visible 17 pages

    Not updated in 180+ days, still pulling 500+ impressions/90d. The narrowest, most explainable case — start here; it's the same rule a human could check by hand.

  2. 2

    CTR-fix review — underperforming for its position 2,182 pages

    Ranking top-3, page-1, or striking-distance, but CTR sits in the bottom quartile for that position tier — not a flat threshold, since a page-3 CTR is never comparable to a top-3 CTR.

  3. 3

    Refresh review, general — model-flagged risk 3,037 pages

    Model score ≥ 0.7 without matching a named archetype. The model still catches real risk the hand-named patterns miss — routed to a more cautious label rather than an invented explanation.

  4. 4

    Manual context check — no reliable position data 51 pages

    avg_position = 0 is the dataset's "no data" code, not a real top rank — the exact pattern behind the model's false negatives. Never act on the model score alone here.

  5. 5

    No action — too new to judge 2,236 pages

    New or under 30 days old. The model's false positives disproportionately land here — pages that haven't had time to earn clicks yet, not genuinely declining ones.

Human review gate

Before acting on any refresh_review* or ctr_fix_review row, a person checks: whether the page has already been updated since the export date (the model can't know this); whether avg_position = 0 or near-zero impressions explains a low score rather than genuine health; whether the page is intentionally quiet for a business reason the data can't see (seasonal content, a page slated for retirement, a paused campaign); and, for CTR-fix candidates, whether a SERP feature above the page is suppressing clicks regardless of content quality — a rewrite won't fix that.

What should never be automated from this output

  • Auto-publishing content edits, rewrites, or AI-generated replacement copy without a human reading the result first.
  • Auto-deleting, de-indexing, or redirecting pages based on no_action or a low model score — the model not flagging a page is not evidence it is safe to remove.
  • Reallocating a client's budget, headcount, or roadmap priorities directly off the queue without a strategist's read.

Monitoring & retrain triggers

  • Performance drift: re-score a fresh trailing-90-day export against a held-out-style client check every quarter; investigate if ROC-AUC drifts more than ~0.05 below 0.743.
  • Base-rate drift: if a future export's declining rate moves far outside the 0.39–0.54 range already seen across this project, the portfolio has changed and needs a fresh look, not just a fresh score.
  • Portfolio composition drift: retrain if more than ~20% of active clients are new since the model was fit — held-out validation only tested generalizing to 6 known-shape clients, not a meaningfully different mix.
  • Human feedback loop: track the share of flagged pages a strategist marks "not actually worth it" after review — a rising rate is a real-world retrain trigger independent of any offline metric.
